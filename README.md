### SecureVault - Сервис шифрования секретов на Go

Стек: Go, AES-256-GCM, PostgreSQL, pgx, Docker Compose.

Проект реализует модель шифрования и хранения секретов в базе данных.

Полные маршруты и назначение:
| Метод и путь | Действие |
| --- | --- |
| POST /secrets	| Создать секрет, вернуть ID |
| GET /secrets/{id} |	Получить исходное значение |
| DELETE /secrets/{id} | Удалить секрет |

и требование авторизации запроса: `Authorization: Bearer <токен>`

Используемые переменные окружения: 
- HTTP_ADDR - адрес http
- DATABASE_URL - подключение приложения к PostgreSQL.
- TEST_DATABASE_URL — подключение интеграционных тестов.
- KEY_ID - идентификатор активного ключа для шифрования новых секретов. Должен присутствовать в ENCRYPTION_KEYS.
- ENCRYPTION_KEYS - JSON-объект, сопоставляющий ID ключей их hex-представлениям. Каждый ключ — 32 байта, представленные 64 hex-символами. Карта содержит активный ключ и старые ключи для расшифрования.
- API_TOKEN - отдельный токен доступа.

Порядок запуска: PostgreSQL → применение миграции → загрузка настроек → сборка и запуск.

Команды запуска: (команды выполняются из корня проекта в Git Bash)

``` bash
    docker compose up -d db
```
для sql:
``` bash
    docker compose exec db psql -U securevault -d securevault
```
Внутри psql нужно выполнить содержимое **migrations/001_create_secrets.sql**, затем выйти через **\q**

Создание файла .env(Пример):
``` dotenv
HTTP_ADDR=127.0.0.1:18080
DATABASE_URL=postgres://USER:PASSWORD@127.0.0.1:15432/securevault?sslmode=disable
KEY_ID=local-key-v1
ENCRYPTION_KEYS='{"local-key-v1":"REPLACE_WITH_GENERATED_KEY"}'
API_TOKEN=REPLACE_WITH_SEPARATELY_GENERATED_TOKEN
```

Настройка, сборка, запуск:
``` bash
set -a
source .env
set +a

go build -o securevault.exe ./cmd/securevault
./securevault.exe
```

- USER и PASSWORD берутся из локального compose.yaml;
- ключ и токен — результаты двух отдельных запусков go run ./cmd/keygen;
- заполнители нужно заменить перед запуском;
- .env исключён из Git и не должен попадать в коммиты.

Реализованы обычные и интеграционные тесты для проверки работы сервиса.
``` bash
    go test ./...
```
При отсутствии TEST_DATABASE_URL тесты PostgreSQL пропускаются, поэтому общий PASS не подтверждает проверку БД. Для неё переменную нужно задать и запустить:
``` bash
    go test ./internal/storage -v -count=1
```

файл **.env** предварительно создается локально и Go автоматически его не читает. 

Для первого запуска генерируется два независимых значения через **go run ./cmd/keygen**.
При последующих запусках сохранённые ключи нужно загружать из .env, а не генерировать заново. Приложение больше не использует переменную ENCRYPTION_KEY.

### Ротация ключей

Для каждого секрета в PostgreSQL хранится key_id. При создании секрета сервис использует активный ключ из KEY_ID, при чтении — ключ с ID из записи в БД.

1. Сгенерируйте новый ключ отдельным запуском `go run ./cmd/keygen`.
2. Добавьте его в ENCRYPTION_KEYS под новым уникальным ID, сохранив прежние ID и значения ключей.
3. Установите KEY_ID равным новому ID и сохраните настройки в локальном .env.
4. Остановите сервер, повторно загрузите .env через `set -a`, `source .env`, `set +a` и запустите сервер. Работающий процесс не перечитывает настройки автоматически.

Пример конфигурации после ротации (значения ключей — заполнители):

```dotenv
KEY_ID=local-key-v2
ENCRYPTION_KEYS='{"local-key-v1":"REPLACE_WITH_EXISTING_V1_KEY","local-key-v2":"REPLACE_WITH_GENERATED_V2_KEY"}'
```

При переходе со старого формата ENCRYPTION_KEY перенесите существующее значение в ENCRYPTION_KEYS под прежним KEY_ID. Новый ключ не должен заменять старое значение под тем же ID.

После перезапуска проверьте чтение старого секрета, создание и чтение нового. В БД у старой записи должен остаться прежний key_id, у новой — активный ID. Повторите чтение после загрузки .env в новом терминале, чтобы проверить сохранение настроек.

Ротация меняет ключ для новых записей: существующие записи автоматически не перешифровываются. Старый ключ нельзя удалять, пока он нужен для чтения записей или восстановления резервных копий. Ключи и API-токен не следует публиковать в README, логах или коммитах.

Текущие ограничения: один общий API-токен, отсутствие разделения прав пользователей, HTTP только для локального запуска, хранение ключей в переменных окружения без внешнего KMS/HSM, отсутствие автоматического перешифрования существующих записей. Это учебный проект, а не production-KMS.

Напоминание: потеря ключа делает сохранённые секреты недоступными для расшифрования.
